## 3. フェーズ 3 で考慮してほしいこと

- **利用者の着想: 時点ごとの指標**（2026-11-24。実装はまだ決めていない）
  - 内容: 再生と組み合わせて、各時点の媒介中心性などの変化を見る。
  - 統括役の答え: 技術的に可能。
    - 年表の区切りごとに部分グラフを作り、Worker で前もって計算してキャッシュし、再生では値を引くだけにする（D-38 と両立する）。
    - 大きさの目盛りは全時点を通した最小・最大にそろえる。
    - 幅のある年代の扱い、日付のないエッジ、その時点にいないノード（欠損として扱う）、小さいグラフでの値の不安定さを決める必要がある。
    - 選んだノードの値の時間変化の折れ線と、時点ごとの CSV があると読みやすい。
  - 設計書 §9.3 の「ノードは、その時点までの累積の次数に応じて大きくなる」と近いので、フェーズ 3 の方針を作るときに一緒に扱うか、利用者に確かめる。要件定義書にはまだ無い。

## 4. 作業の進め方（このセッションで固まった手順）

- **言葉**: 利用者への返事は日本語で書く（利用者の指摘。途中で英語になっていた）。コード、文書、コミットの文言も日本語。識別子は英語。
- **役割**
  - 統括役は計画、統合、確認、文書の更新を行う。実装は役割ごとのエージェントに任せる（`.claude/agents/`）。
  - 実装のたびに reviewer に確認させ、指摘を実装者へ戻す。
  - 利用者の報告への小さな対応は、統括役が直接直してもよい。
- **並行作業**: worktree で分ける。
  ```bash
  git worktree add -b wip/<task> /home/user/wt/<task> HEAD
  ln -s /home/user/Relata/node_modules /home/user/wt/<task>/node_modules
  ```
  - `/node_modules` は git の info/exclude に入っている。
  - エージェントはコミットしない。統括役が worktree でコミットし、作業用のブランチへ `git merge --no-ff` で統合する。
  - 終わったら `git worktree remove --force` と `git branch -D wip/<task>`。
  - エージェントが worktree で `npm install` すると、シンボリックリンクが実ディレクトリに置き換わる。依存を足したときは、統合後に本体で `npm ci` を実行する。
- **Node**: `export PATH=/opt/node24/bin:$PATH`（既定の node は 22 系）。
- **E2E**
  - 一時の設定 `playwright.local.config.ts` を作る。コミットせず、使い終わったら消す（format:check で引っかかり、停止フックが未追跡のファイルを指摘するため）。
    ```ts
    import base from './playwright.config';
    export default { ...base, use: { ...base.use, launchOptions: { executablePath: '/opt/pw-browsers/chromium' } } };
    ```
  - **spec は `test` を `./fixtures` から import する**（`tests/e2e/fixtures.ts`。localhost 以外への要求を止め、OSM のタイルを小さな PNG に差し替える。OSM の利用規約で自動の操作からタイルを取らないため。`@playwright/test` から直接 import すると lint で止まる）。手でスクリーンショットを撮るスクリプトでも、`context.route` で外部への要求を止める。
  - 実行: `npm run build` の後、`RELATA_E2E_PORT=<番号> E2E_SKIP_BUILD=1 npx playwright test -c playwright.local.config.ts --trace off`。
    - `E2E_SKIP_BUILD=1` は `dist/` を使い回すので、ビルドし直すのを忘れない。
    - 並行して動かすときは、ポートを分ける（統括役 4320、エージェント 4321〜4324、性能 4194）。
  - 公開サイトに対して実行するときは、`baseURL: 'https://qsarkbir.github.io/Relata/'` と `webServer: undefined` を足した一時の設定を使う。
  - **不安定さの確かめ方**
    - 修正の後は、関連する spec だけでなく全 spec を実行する。
    - ドラッグや座標を使うテストは、`--repeat-each=3〜5 --workers=4 --retries=0` で負荷をかけても通ることを確かめる。CI のほうが遅く、手元で通っても落ちることがあった。
    - 座標は位置が落ち着いてから取る（`tests/e2e/timeline.spec.ts` の `stableBox`）。数える範囲は操作の範囲とそろえる（`range-select.spec.ts`）。
- **CI と GitHub**
  - GitHub の操作は MCP の GitHub の道具を使う。`gh` は検索と、`gh run view` / `gh run list` の確認だけにする（GraphQL は使えない）。
  - CI の失敗は `gh run view <id> --log-failed` で見る。
  - PR は統括役が作る。**main への統合は利用者が行う**。
  - PR を作ったら `subscribe_pr_activity` で見守り、失敗は原因を直して push する。
  - 統合の後は、`git fetch origin main` と `git checkout -B claude/<ブランチ> origin/main` で揃え、通常の push で進める（force push は使わない）。
  - Pages への配信の失敗（artifact が見つからない）は、PR #49 で直した。まだ 1 回しか確かめていないので、次の配信も見る。
- **進行表の規則**: タスクの開始時と完了時に更新する（進行表の末尾の「更新の規則」）。設計を変えたら、設計書の版を上げ、進行表の更新履歴に書く。
- **使用量の上限**: エージェントが 5 時間の上限で止まったら、リセットの後に SendMessage で同じエージェントを再開できる（作業は残っている）。
- **後片付け**: エージェントが作った一時ファイル（Python の wheel など）がリポジトリの直下に残ることがある。停止フックが「未追跡のファイル」と言ったら、中身を確かめてから消す。

## 5. 利用者の判断と好み（このセッションでの記録）

- PDF のフォントは D-43 の補足のとおり。文字を輪郭で描き、検索できないことを受け入れた（統合済み）。
- 再生の薄い表示は、書き出しにも既定で含める。「書き出し」のダイアログで外せる（利用者の指摘による）。
- 再生の操作は条件の行に置かない。時刻の表示は、図の窓の角の小さな文字にする（利用者の提案）。
- ノードとエッジは小さめが好み（「1/4 程度でも十分」）。
- 実装の前に、方針の案を見せて承認を受ける進め方（フェーズ 2 と同じ）。
