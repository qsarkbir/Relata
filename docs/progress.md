### クラウドで作業するときの手順
クラウドのセッションは、GitHub の `main` を新しく取得したところから始まる。手元のマシンにだけあるものは使えない。

- **最初に一度だけ行う準備**
  1. `npm ci`（Node は 24 系。`.nvmrc` と `.npmrc` の engine-strict を参照。合わなければ止まる）。クラウドの既定の `node` が 22 系のときは、`/opt/node24/bin` を `PATH` の先頭に足す
  2. `npx playwright install --with-deps chromium`（E2E を動かすときだけ）
  3. `python -m pip install networkx convertdate`（正解値を作る T1-02、T1-09 のときだけ）。クラウドでは convertdate の依存の pymeeus がシステムの Python で組み立てられないことがあるので、仮想環境（`python3 -m venv <場所>` の後、その `bin/pip install networkx convertdate`）に入れる
  4. `npm run typecheck`、`npm run lint`、`npm test` が通ることを確かめる
- **手元にしかないもの**
  - `upstream/`（旧 Palladio のソース）は Git に含めていない（設計書 §17）。要点は `docs/filter-audit.md` と設計書 §13 にある。中身を読む必要があれば、GitHub の `humanitiesplusdesign` の Palladio のリポジトリを `upstream/` に取得する（変更しない、ビルドに含めない）。
  - 統括役のメモリ（`~/.claude/` の下）は引き継がれない。判断の材料は、この進行表、設計書 §2 の決定事項（D-01〜D-19）、「設計の論点」（R-01〜R-13）にすべて書いてある。
- **`main` への統合**: クラウドのセッションでは、統括役はタスクのブランチを push して PR を作るところまで行う。**`main` への統合は、利用者が PR を確認して行う**（2026-11-19 の利用者の指示）。リモートのブランチの削除もクラウドのセッションからはできないので、利用者が行う。
- **E2E**: Playwright の期待する Chromium の版がクラウドに無いときは、`/opt/pw-browsers/chromium` を `launchOptions.executablePath` に指定した一時の設定（コミットしない）で動かす。
- **進め方**（これまでと同じ。設計書 §16、§18）
  - タスクごとにブランチ（`t1-26-text-keys` など）を作り、担当のエージェント（Sonnet）に実装させ、reviewer（Opus）に確認させる。並行させるときは worktree を分ける。
  - 統括役が `typecheck`、`lint`、`format:check`、`test`、`build`（画面に関わるなら `test:e2e`）を確かめ、進行表を更新してコミットし、ブランチを push して GitHub の CI が通ってから `main` に統合する。`main` への push で GitHub Pages に配信される。
  - GitHub の設定の変更（`main` の保護など）は、利用者に確かめてから行う。

## 更新の規則（統括役向け）
- タスクを始めるとき: 状態を 🔄 にし、「現在地」の「作業中」を書き換える。
- タスクが終わったとき: [設計書 §20](design.md) の完了の定義を確かめてから ✅ にし、完了日を書く。「現在地」の「直近の完了」「次にやること」と、「フェーズの概要」の進み具合を書き換える。
- 要件や設計を変えたとき: 該当文書の版を上げ、「更新履歴」に書く。
- 未決事項が決まったとき: 状態を「決定」にし、内容を設計書 §2 に移す。
